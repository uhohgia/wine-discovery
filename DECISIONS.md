# Decisions and assumptions

## Scope
- Wine Discovery **replaces** the earlier Restaurant Journal screens in this repo. The old app is archived in `_archive/restaurant-journal.tar.gz` (there is no git history). Its Supabase tables, trigger and sample data are untouched.
- No deployment is set up. Not a git repository (by choice, for now).
- The shelf **starts empty**: users add bottles from the catalog.

## Kept from the earlier app
Supabase client, email/password sign-in (sign-up, sign-in, password reset), design tokens, Button/Card/Chips/Switch, PWA setup, Vitest + Playwright + axe.

## Auth
- Real accounts use Supabase email + password. Demo mode (no env vars) uses device-only accounts and **does not check passwords**; it exists so the app and tests run offline.
- The signed-in person is read from the auth session only. The app does **not** read or write the old `profiles` table.
- Known leftover: the old database trigger `on_auth_user_created` still creates a row in the old `profiles` and `events` tables for each new account. It's harmless; it can be dropped later, with your OK.

## Data model
- New tables are all `wd_`-prefixed (see `supabase/migrations/20261107200000_wine_discovery.sql`).
- `wd_taste_profiles` holds one row per user: `prefs` (empty `{}` until the quiz is done), `rating_count`, and `age_confirmed_at` (the one-time 21+ confirmation; an addition to the brief's columns). Confirming age before the quiz creates the row with empty prefs.
- `pairings` is free text shown on the wine card (e.g. "Roast chicken"); `occasions` uses the controlled list. The ranking logic uses attribute-based rules, not these strings.
- Controlled vocabularies live in `src/data/vocab.ts` and are mirrored by CHECK constraints. A unit test fails if they drift apart. Whites and sparkling wines must use `low` tannin.
- Ratings and events can be added, read and deleted by their owner, never edited. Deleting powers "delete my data".
- The catalog (`wd_bottles`) is readable by signed-in users only and has no client write access (policies and revoked privileges).
- Deleting a bottle also deletes shelf items and ratings that point at it.

## Accessibility and design
- Base text is 18px (`html { font-size: 112.5% }`) so all rem sizes scale with the reader's own text settings. Tap targets are at least 44px.
- Every page carries the footer "Tasting notes by a fellow beginner, not a sommelier." and "Please enjoy responsibly."

## Applied to Supabase (project `arhuymvyhgvfbqoekcgh`)
- Both Wine Discovery migrations were applied with your approval: the five `wd_` tables with RLS, and the 10 placeholder bottles.
- Verified by simulating two users and a signed-out visitor (rolled back): nobody can see or change another person's shelf, profile, ratings or events; the catalog can't be written from the client; signed-out visitors can't read anything; unknown vocabulary, oversized events and unknown bottles are rejected; ratings and events can't be edited; users can delete their own rows; deleting an account removes its rows.
- Supabase advisors: no findings on the new tables. The remaining notes belong to the earlier app (the public view, helper functions, `admin_emails`) plus **leaked-password protection is off** (a dashboard setting under Auth, may need a paid plan).

## Milestone (b): 21+ gate, quiz and taste profile
- **Taste profile model:** a 0 to 2 *target* for body, sweetness, zing (acidity), tannin and fruit style (or none = "not sure"), plus -1 to 1 *affinities* for wine types and for fruit, flower and extra notes. Stored in `wd_taste_profiles.prefs`, validated with Zod on every read (unreadable data becomes an empty profile). The quiz answers are stored inside `prefs.quizAnswers` so "Edit my answers" can reopen the quiz filled in.
- **How answers map** (all in `src/data/quizRules.ts`): milk skim/2%/whole is body 0/1/2. Coffee sugar none/little/sweet is sweetness 0/1/2 (an analogy, not a promise). Black tea "dries my mouth and I like it / don't / not really" is tannin 2/0/1. Lemonade question is zing 0/1/2. "Fresh" vs "jammy" fruit is 0 vs 2, and "either" is no preference. Picked fruits and scents become liked notes (1). "None of these" nudges every flower and extra note to -0.3. Picked wine types are liked (1) and the other offered types count as a mismatch (-0.6); orange and "other" aren't asked, so no opinion.
- **"Not sure" and skipping are the same:** they tell us nothing, and the profile just stays unknown on that dimension.
- **"Show me wines now"** appears from screen 3 onward. It saves what has been answered so far (at least as much as the person had before, when editing) and logs `quiz_stopped_early` with the screen and the number of screens answered.
- **Profile names:** 9 rules, first match wins, ending in a fallback "Curious Explorer". People who stop very early often get that name, which fits.
- **Re-taking the quiz replaces the profile** with one built from the new answers. Once ratings exist (milestone e) I'll replay them on top so edits don't erase what ratings taught the app.
- **21+ gate:** an honor-system question, asked once and remembered as `age_confirmed_at`. Answering "No" stores nothing and offers a way out. Every screen except sign-in checks it, so it can't be skipped by typing an address.
- **Demo mode** stores the same data in the browser (`localWdRepo`) so the whole flow works without Supabase; it is also what the automated tests use.
- **Bug caught by a test:** tapping "Yes" raced two redirects and sometimes landed on Home instead of the quiz. Fixed by letting a single redirect decide.
- **Accessibility so far:** automated axe checks (WCAG A and AA) pass on every screen; the quiz works by keyboard alone (focus moves to each new heading); selected answers show a check mark and filled background, not just color; nothing scrolls sideways at 390px at the default or 200% text size; all tap targets are 44px or more. Scale labels stack automatically when text is large. A manual screen-reader pass is still to do in milestone (g).
- **Events logged so far** (to `wd_events`): `quiz_started` (`editing`), `quiz_completed` (`steps_answered`), `quiz_stopped_early` (`at_step`, `steps_answered`). Example check: `select name, count(*) from wd_events group by 1;` and the share who finish: `select count(*) filter (where name='quiz_completed')::float / nullif(count(*) filter (where name='quiz_started'),0) from wd_events;`.

## Milestone (c): wine card and My shelf
- **Scoring is in this milestone, not the next:** the wine card has to say "will you like it?", so `scoreBottle`, `confidenceFor` and `explainWhy` (in `src/lib/scoring.ts`) are built and unit-tested now. Milestone (d) adds the meal pairing rules and ranking on top.
- **How a bottle is scored (0 to 1):** each thing we know about the person is compared with the bottle and weighted (type 3, body 2, sweetness 2, flavors 2, zing 1.5, grip 1.5, fruit style 1, flowers 1, spice/smoke 1). A target on the 0 to 2 scale matches by distance (`1 - gap/2`); liked flavors match by how much the person likes the flavors the bottle has. Things we don't know are skipped, not counted as zero. A type the person steers away from multiplies the score by 0.5, a strong penalty. All numbers are in `src/data/scoringWeights.ts`.
- **Confidence labels:** "A good bet" needs a score of at least 0.72 **and** either an easy-to-like bottle or 3+ ratings. A high score without that is "Worth a try". "Worth a try" starts at 0.52; below that is "A stretch". With no taste profile yet there is no label at all, just an invitation to take the quiz.
- **The "why" is plain words,** built from the strongest matches ("It's light and fresh, just the way you like it. It has the red-berry flavors you like.") and always names a clash honestly ("But it's full-bodied and jammy, and you like lighter wines."). A test checks that no sentence ever contains wine jargon.
- **Quirk worth knowing:** a person who only answered "red" and "skim" sees a full-bodied red as "Worth a try" (the type matches, the body doesn't), which seems right. More answers make the labels sharper.
- **Price feel:** `$` under 15, `$$` 15 to 30 (inclusive), `$$$` over 30, as constants in `src/data/pricing.ts`. Screen readers hear "Easy on the wallet, about $14" instead of dollar signs.
- **Tap-a-word helper:** flavor words and "Wine words" are buttons; tapping one shows its meaning in a live region and tapping again closes it. The four feel scales have a "What's this?" disclosure, with the technical word ("tannin", "acidity") one tap away rather than on the surface. Every flavor note and wine type must have a glossary entry (a test checks).
- **Catalog search** matches the start of whole words across name, producer, type, how it tastes ("light", "bold", "crisp", "bubbly"), flavors and foods, so a "3" doesn't hit a 2023 vintage. Name and style matches rank first. The same search will power the typed fallback in the scan milestone.
- **Shelf:** adding a bottle again changes bought/gift instead of duplicating. Each person's shelf is private (row-level security, tested earlier). The catalog is read from `wd_bottles`; each row is checked against the strict bottle schema and an unreadable row is skipped, not shown.
- **Navigation:** Home, My shelf and My taste, as a wrapping row under the header (no fixed bar to cover content, and it wraps at large text). The current page is marked with a thick underline and `aria-current`, not color alone.
- **Not on the wine card yet:** the Rate button arrives with milestone (e).
- **Event:** `wine_card_viewed` (`bottle_id`, `on_shelf`), once per visit to a card. Events are fire-and-forget, so one sent just as the page reloads can be lost.
- **Accessibility:** axe (WCAG A and AA) passes on the shelf, add-bottles and wine card screens, including with every explanation open; nothing scrolls sideways at 390px at the default or 200% text; every tap target is 44px or more. Confidence labels differ by words and symbol, not just color.

## Milestone (d): home, pairing and ranked results
- **Home** is now "What are you eating?": 7 meal tiles and 4 occasion tiles that flow into as many columns as fit (measured in text-size units, so large text simply stacks them). Tapping a tile opens `/eat/<id>`. The quiz prompt, shelf summary and taste name sit around it.
- **Pairing rules are data** (`src/data/pairingRules.ts`): for each meal or occasion, an ideal spot on each 0 to 2 scale with a weight, how well each wine type suits it (-1 to 1), and for occasions an "easy to like" weight, a cheaper-or-pricier preference and a bonus for bottles tagged with that occasion. Examples from the brief: spicy takeout wants off-dry, soft (no grip) and zippy; BBQ wants a bigger body, some grip and ripe, jammy fruit. Each rule also carries the plain sentences used to explain a match ("A touch of sweetness calms the heat.") or a miss. A test fails if a rule scores something it can't explain, or if an explanation uses jargon.
- **Ranking blends 50/50:** `combined = 0.5 x pairing + 0.5 x taste` (`PAIRING_WEIGHT` in `pairingRules.ts`). Ties break by taste, then name. Before the quiz there is no taste to blend, so the list ranks by the food alone, shows no confidence labels, and says so.
- **The label on a ranked bottle is about that meal.** It uses the same thresholds as the wine card but runs on the *blended* score, so a bottle that suits you but is a poor match for the meal reads "Worth a try" here while its wine card (taste only) may say "A good bet". Each result still explains both halves: why it does or doesn't go with the food, then how it sits with your taste ("It's a white, and you usually reach for red.").
- **Taste still wins when it's strong:** a big-red lover asking about spicy takeout gets their big red first and the textbook off-dry white last, labelled "A stretch", with the pairing sentence still telling them why that white would normally be the classic. That felt more honest than hiding either half.
- **Gift** ranks by whether a bottle is tagged for gifting, is easy to like and feels like a gift (not too cheap), blended with your taste. It does not try to guess the recipient's taste; the "gift mode" idea is a concept preview in milestone (f).
- **Event:** `meal_selected` (`kind`: meal or occasion, `id`, `shelf_size`), once per visit to a results page.
- **Empty shelf:** a friendly prompt to add bottles. Only bottles on the shelf are ranked.
- **Not yet:** "not for me" ratings that visibly change these rankings arrive with milestone (e); the ranking already responds to a changed profile (tested).

## Milestone (e): rating and the dislike decoder
- **Flow:** a "Rate this bottle" button on the wine card opens `/bottle/<id>/rate`: Loved it / It was fine / Not for me. "Not for me" asks "What didn't you like? Pick any that fit." with the brief's reasons (too dry, too sharp or sour, too heavy, too sweet, mouth-drying or bitter, too light or watery, didn't like the flavor) and "Not sure". After saving, a warm confirmation, a link to the taste profile and a way back. Everything is optional except the first choice.
- **How a rating changes the profile** (`src/lib/rating.ts`, numbers in `src/data/dislikeRules.ts`):
  - **Loved it:** every known scale target moves 35% of the way toward the bottle; where we knew nothing yet it adopts the bottle's value. The bottle's type and flavors become 0.3 more liked.
  - **It was fine:** a light 10% nudge toward the bottle, and only where we already had an opinion (so a "fine" on an empty profile teaches nothing).
  - **Not for me:** each reason moves its scale a full notch *past* the bottle, away from it: too dry means sweeter, too sharp means smoother, too heavy means lighter, too sweet means drier, mouth-drying means less grip, too light means fuller. It never moves toward the bottle from where the person already was, and never off the ends of the scale. "Didn't like the flavor" makes each flavor in the bottle 0.4 less liked. "Not sure" changes nothing but is still logged. A "not for me" with no reason changes nothing either, so we don't guess.
- **Why a full notch:** with a smaller step, one "too sharp" on a zippy bottle barely changed how bottles were described. A full notch lands "too sharp" on *balanced*, halfway to smooth, which is the safest reading of a single complaint, and it visibly changes later explanations and scores.
- **Confirmations** are warm and specific ("Good to know. We'll steer away from sharp wines."); several reasons join naturally; "flavor" names the actual flavors; a test checks none ever sounds like blame or contains jargon.
- **Every rating is kept.** The latest one shows on the wine card and the shelf, and every rating adjusts the profile once. The profile's rating count is the number of ratings.
- **Retaking the quiz keeps what ratings taught the app:** the new answers become the starting point and every past rating is replayed on top, in order (`replayRatings`). Tested, including that skipping the replay would give a different result.
- **No half-saved ratings:** the rating is saved first, then the profile; if the profile update fails, the rating is taken back out.
- **Ratings can start a profile.** Someone who rates before taking the quiz gets a profile built from ratings alone (the rest stays "not sure"). The quiz prompt on Home then goes away. Easy to change if you'd rather keep nudging.
- **Events:** `rating_saved` (`bottle_id`, `verdict`, `reasons_count`) and `dislike_reason_selected` (`bottle_id`, `reason`, one per reason, including "not-sure"). Example: which reasons come up most: `select properties->>'reason' as reason, count(*) from wd_events where name = 'dislike_reason_selected' group by 1 order by 2 desc;`
- **Accessibility:** axe (WCAG A and AA) passes on every rating screen (nothing picked, the validation message, "not for me" with reasons, the thank-you, the wine card and shelf with a rating); nothing scrolls sideways at 390px at the default or 200% text; selected answers show a check mark and filled background.

## Milestone (f): simulated scan and concept previews
- **Scan is simulated and says so.** `/scan` has a "Simulated scan" banner and one big button. It picks a bottle from the person's shelf (never the one it just picked, if there is any other choice) and opens its wine card, which notes "Found by scan". With an empty shelf it picks one of the sample bottles instead, so a scan always works; the wine card then offers "Add to my shelf". No camera, no photos, nothing leaves the device. The pretend "reading the label" moment is 0.5 seconds (`SCAN_DELAY_MS`).
- **The typed fallback is always there,** under the scan button: "Can't find it? Type the name or describe it." It searches the catalog with the same word search as "Add bottles" (name, maker, how it tastes, flavors, foods), so "light red" or "crisp white" work. It runs when you submit, not on every keystroke. No match shows a kind message and a link to every bottle.
- **Events:** `scan_simulated` (`source`: shelf or catalog, `bottle_id`), `scan_fallback_used` (`query_length`, `results`; **never the words typed**), and `concept_screen_viewed` (`screen`), the last once per visit.
- **Six concept previews** under `/ideas` (listed on an "Ideas we're testing" page and linked from Home): an alcohol-free option, gift mode, stay on budget, where to buy it, host card, and more from this producer. Every one opens with a "Concept preview" banner saying "This isn't built yet… nothing on this screen works", and none contains a button, a text box or a checkbox, so nothing pretends to work (a test enforces this for all six). The mock-ups use real catalog data where that's harmless: the budget screen's counts follow the real price thresholds; the store, host-card and producer sketches use the placeholder bottles' own details.
- **Alcohol-free is shown as a normal choice,** alongside wines in the sketch, as the brief asks.
- **A reliability fix found in testing:** an analytics event sent a moment before the person leaves the page could be cancelled by the browser (one `scan_fallback_used` was lost this way). Event writes now use `keepalive`, so the browser finishes sending them; nothing else about the requests changes (`src/lib/keepalive.ts`, tested). Events are still fire-and-forget, so a rare loss is possible.
- **Navigation** now reads Home, Scan, My shelf, My taste (it wraps onto a second row at large text).
- **Accessibility:** axe (WCAG A and AA) passes on the scan screen (empty shelf, with results, with nothing found), the ideas list and every concept preview; nothing scrolls sideways at 390px at the default or 200% text; all tap targets are 44px or more.
- **Still a stretch goal, not built:** real label recognition (an Edge Function calling a vision model, with the typed fallback kept). Only if you ask.

## Milestone (g): polish, accessibility and delete-my-data
- **Delete my data** (You screen). A red button opens an inline "Delete everything?" box (focus moves to it; "Keep my data" backs out). Confirming removes the person's ratings, shelf, activity and taste profile, then sends them back to the 21+ question, as a new person. **The sign-in account itself stays**: deleting an auth user needs the project's secret key, which must never be in a browser, so it would need a small server function. That is the one honest gap against "delete my data"; today the owner can remove a sign-in from Supabase → Authentication, which also cascades to every `wd_` row. Verified live against the real project with a throwaway account: all four tables showed 0 rows afterwards.
- **Page structure on every screen:** one `h1`, no skipped heading levels, one `main`, a labelled "Main" menu, the footer ("Tasting notes by a fellow beginner, not a sommelier." / "Please enjoy responsibly."), `lang="en"`, and a unique "… · Wine Discovery" page title on each of 18 routes. A Playwright test checks all of it.
- **Keyboard:** a "Skip to content" link is the first Tab stop. On every change of screen, focus moves to the top of the new page and the view scrolls up, so a keyboard or screen-reader user isn't left in the middle of the old one. (Found while testing: React's development mode ran this on first load too and stole focus from the skip link. Fixed by only moving focus when the address really changes.) Rating a bottle and deleting data both work with the keyboard alone, and every Tab stop shows a visible focus ring (tests walk the whole page).
- **Sizes:** nothing scrolls sideways at 320, 390, 768 and 1280px, and the reading column stops at about 36rem so lines stay readable on desktop. 200% text at 390px is checked on every screen as in earlier milestones.
- **Offline and errors:** the production build is an installable app ("Wine", opens full screen) whose screens are cached after the first visit; offline it opens, shows an "You're offline" bar, and works for anything already on the device. Writes made offline are not queued (they show a kind error). An error boundary catches an unexpected crash and shows a friendly "Something went wrong" with a way home instead of a blank page.
- **Secrets:** a test scans the source for service keys, secret keys, JSON web tokens, Anthropic keys and private keys, and checks `.env.example` holds only the two `VITE_SUPABASE_*` names. The app only ever uses the publishable key.
- **Clean-up:** removed code the journal left behind that Wine Discovery doesn't use (`form.tsx`, `format.ts`, `vercel.json`). No deployment is configured, as agreed.
- **`supabase/validation_queries.sql`** holds the queries for judging the idea (quiz funnel, where people stop, popular meals, dislike reasons, rating split, fallback with no match, concept interest). All ran successfully against the live database.

## Real bottles and photo scanning (after milestone g)
- **Update: photo scanning is switched off for now, by request.** Scan is simulated for everyone (accounts included), with its "Simulated scan" banner. The photo scanning code, the `scan-label` function (deployed, version 2, no Anthropic key set, so it just answers "not set up") and the two migrations all stay, ready for later. Turn it on with `VITE_PHOTO_SCAN=1` (see the README). The notes below describe how it works when on.
- **Your 10 bottles replace the placeholders.** `src/data/bottles.json` is now your real catalog. The 10 made-up bottles moved to `src/data/bottles.sample.json` and are used only by the automated tests (`VITE_CATALOG=sample`, set in `vite.config.ts` and for the main e2e server), because about 250 test lines depend on names like "Sample Red 1" and the tests shouldn't change when you edit your catalog. A separate e2e project (`real`, port 5175) runs on the real catalog.
- **Naming:** the wine card's big title is the wine's own name ("Anderson Valley Pinot Noir"), with the maker under it ("Goldeneye · 2022"), as the app already worked.
- **First-draft guesses, please review.** Name, maker, year and type are read straight from your labels (two bottles, Moët and Decoy, have no year, so none is shown; Beachaven's rosé shows none either). Everything else is my best reading of the label text and general knowledge, not tasted or looked up: **prices** (Moët $55, Decoy $25, Canvasback $35, Goldeneye $55, Story $35, Clos du Val $75, Beachaven $16, Migration $45, Duckhorn $25, Dr. Loosen $20), **body, sweetness, acidity, tannin, flavors**, "easy to like", where it's sold, serving tips and talking points. A few come from the back labels (Migration: peach, Fuji apple, citrus; Dr. Loosen: crisp, juicy, 8% alcohol, "tasty with spicy foods"; Story: made in a qvevri). Beachaven's sweetness (off-dry) is a guess. These feed the recommendations, so a wrong guess gives a wrong "Will you like it?".
- **Photos.** The 10 front photos are shipped, shrunk to ~600×800 JPEGs of about 90 KB (`public/bottles/<id>.jpg`, 0.9 MB in all), shown as a small thumbnail in lists and a larger photo on the wine card. They aren't pre-downloaded for offline use (that would 5× the app's first download); each is cached the first time it's viewed. They're your own phone photos with a hand and a cluttered table in the background, cropped to the label area as well as a fixed crop can; clean product shots would look better. The 10 back photos are not in the app: they are kept in `bottle-photos/` as test material for the label reader.
- **Photo scanning reads the label; it doesn't recognize bottles by their look.** Claude is asked only to transcribe the maker, wine name, year and type from the photo (JSON in a fixed shape, nothing guessed from outside knowledge). The app then matches that text to the collection (`src/lib/matchLabel.ts`): the maker's name counts double, one misread letter in a long word is forgiven, a different year still counts as the same wine, a wrong type counts against it, and with no maker on the label (Clos du Val's front shows none) only a matching year makes it a sure match. Three outcomes: **match** (opens the card), **similar** ("Is it one of these?"), **not in the collection** ("We don't have that one yet", with the typed search started for you). A photo that isn't a wine label gets its own message. The matching numbers are named constants at the top of that file.
- **Why a function.** The Anthropic key must stay on a server, so the browser calls the `scan-label` Edge Function with the person's login. It checks the login, limits each person to 30 reads an hour (a tally table `wd_scan_calls`, readable only by the function), keeps no photo and no result, and logs only what kind of failure happened. It uses `claude-haiku-5-5`, the cheapest current model, chosen because this is a personal MVP and the goal is the lowest cost: list price is $0.10 per million input tokens and $0.50 per million output, so as an estimate (not measured) a scan is a few hundredths of a cent and 1,000 scans are well under a dollar. Low effort, and a fixed JSON shape. Haiku has no server-side refusal fallback, so a declined request is just reported as "couldn't read that". The API is billed per token to the Anthropic API account (not covered by any Claude subscription); a prepaid balance or a monthly spending limit in the Anthropic Console caps it, and the app already limits each person to 30 scans an hour. If Haiku misreads some of your 20 photos, `claude-sonnet-5-5` is the next step up (a one-line change in `LABEL_MODEL`).
- **Privacy.** The photo leaves the phone for one request to Supabase and Anthropic and is not kept by us. The screen says so ("Your photo is sent securely to be read. We don't keep it."). The new event `scan_photo` records only the outcome (matched, similar, unknown, not-label, error and its kind), never the photo or the words read. "Delete my data" doesn't remove the scan tally (rows holding only a user id and a time); it disappears when the sign-in account is deleted.
- **Demo mode keeps the simulated scan** (no Supabase means no function to call), with its banner. Scan on an account without the function deployed shows "Photo scanning isn't switched on yet" and the typed search still works.
- **Development-only pretend reader** (`VITE_FAKE_SCAN=1`, `src/lib/fakeLabelReader.ts`): lets the browser tests and a person on `npm run dev` use the screen with no Claude. It is behind `import.meta.env.DEV`, so the production build contains none of it (checked by searching the build).
- **Layout fix found by the new tests:** at 200% text on a 390px phone, long real names ("Keefer Ranch Chardonnay") pushed the page sideways. The small bottle photo is now a fixed 56px, and very long words in names may break onto the next line instead of scrolling.
- **Honest gaps for this change:** (1) The label reader has **not been run against the real Claude API from here** (no key in this environment, so no deploy and no live test); everything around it is unit-tested with a stand-in, and `LIVE_SCAN=1 npm run test:e2e:cloud -- scan-photos` is the check to run first. The exact request shape (structured output on Haiku 5.5) is written from Anthropic's documentation, not yet observed to work. (2) The matching was tested on what a good reader *would* say about your labels, not on what Claude actually says. (3) iPhone HEIC photos should arrive as JPEG from the file picker; not tested on a real iPhone. (4) The database changes (new scan table and event name; your 10 bottles) **are applied** and the function is deployed (version 2). (5) In live tests from one machine, sending a photo to the function stalled intermittently (the browser got through the preflight but the POST didn't arrive); the app now gives up kindly after three tries, but the cause is unexplained. Try it on a real phone before relying on it.
